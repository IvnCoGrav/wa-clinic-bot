## 6. Analisis Deduplikasi & Klaster Lintas Modul (Cross-Cutting Clusters)

### C1 — Kredensial, Rahasia & Pemindaian Kode (P0)
- **Anggota klaster:** `S-001` (kredensial tracked di repo publik), `S-013` (secret scanner parsial), `DEL-01` (CI pipeline rahasia), `DEL-03` (kebocoran build context .dockerignore - *FIXED*).
- **Akar masalah:** Kredensial operasional tercatat di panduan manual; scanner hanya memindai staged diff tanpa mode `--all`.
- **Solusi fondasional:** Purge & rotasi kredensial live; jadikan scanner default `--all` di CI gate `.github/workflows/ci.yml`.

### C2 — Otorisasi Fail-Open, RBAC & Isolasi Multi-Tenant (P0/P1)
- **Anggota klaster:** `S-002` (whatsapp-provider QR/disconnect), `S-003` (role tanpa scope = allow), `Cfg-012`/`Cfg-013` (endpoint config default-allow), `API-02` (staf impersonation default-tenant), `API-03` (login staf default-tenant), `D-02`/`D-03` (seam customer update).
- **Akar masalah:** Deny-list berbasis URL prefix yang rapuh alih-alih allow-list per peran terverifikasi; query database tanpa klausa `tenant_id` wajib.
- **Solusi fondasional:** Ubah otorisasi menjadi default-deny; wajibkan scoping `tenant_id` pada seluruh method repository dan rute API; seed scope lengkap.

### C3 — Keandalan Cadangan Data (Backup & Restore Durability) (P0)
- **Anggota klaster:** `I-001` (backup GDrive plaintext tanpa enkripsi), `I-002` (restore tanpa tenant check), `K-003` (backup mingguan parsial dilaporkan sukses), `DEL-07` (skrip backup host broken & unencrypted).
- **Akar masalah:** Fallback programmatic menelan error; tidak ada verifikasi row-count dan enkripsi AES-256-GCM kanonis.
- **Solusi fondasional:** Standarisasi backup terenkripsi AES-256-GCM via `verify-backup-restore.ts`; verifikasi checksum & baris sebelum klaim sukses.

### C4 — Durabilitas Ingress & Idempotensi Pesan (P0/P1)
- **Anggota klaster:** `W-005` (pre-log sebelum enqueue), `W-001` (turn macet tanpa sweep periodik), `ING-02` (*FIXED* di S1), `ING-07` (*FIXED* di S1), `K-004` (Sheets outbox race condition), `I-003` (Sheets atomic lease).
- **Akar masalah:** Pencatatan status sukses sebelum pesan durable di BullMQ; absennya background sweep aktif untuk turn macet.
- **Solusi fondasional:** Urutan pipeline kanonis: `persistInbound -> enqueue -> claimMessageId`; background cron recovery turn dengan rate limiting.

### C5 — Scheduler Background Cron, Lock & Lifecycle (P1)
- **Anggota klaster:** `K-001` (ketiadaan advisory lock / heartbeat), `K-002` (jadwal setInterval non-persisten), `K-007` (nightly report state RAM), `Ar-001` (shutdown setInterval liar), `Ar-007` (cron overlap), `SM-10` (timer burst coalesce).
- **Akar masalah:** Worker mengandalkan `setInterval` memori lokal tanpa PostgreSQL advisory lock atau tabel run log.
- **Solusi fondasional:** Pasang `pg_try_advisory_lock` pada proses worker; implementasikan heartbeat tabel `CronRunLog` dan interval terdaftar di `interval-registry.ts`.

### C6 — Gerbang Klinis, Skrining & SOP Medis (P0)
- **Anggota klaster:** `A-003` (evaluasi vaksin/demam fail-open), `C-005` (SOP vaksinasi kontradiktif), `C-006` (grounding RAG miss), `CFG-01` (keyword darurat kejang tertutup non-medical phrase), `CFG-06` (katalog medis hardcoded), `Cfg-005` (SOP/FAQ hardcoded).

- **Solusi fondasional:** Otoritas klinis dominan deterministik: tri-state screening (unsafe > safe), evaluasi kata kunci darurat prioritas tinggi, sinkronisasi penuh dari database `ClinicPolicy`.

### C7 — Kontrak Tool & Komitmen Transaksional (P0/P1)
