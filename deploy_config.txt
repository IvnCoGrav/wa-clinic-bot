# Deployment & Version Pinning Notes — WAHA Clinic Bot

## Pinned Versions
*   **WAHA Container Image:** `devlikeapro/waha:noweb-2026.7.2` (Engine: NOWEB)
*   **Database:** `postgres:16-alpine`
*   **Backend Node Version:** `>=20.x`

## Historical Version Context & Fixes
*   **2026-07-29 (Update to WAHA 2026.7.2):**
    *   **Reason:** WAHA NOWEB version `2026.7.1` had a critical regressive bug where connection to WhatsApp Web servers failed during the Noise Handshake process (reference: GitHub issue `devlikeapro/waha#2198` and similar historical regressions like `#1495`, `#1509`). Sesi tersangkut secara permanen di status `STARTING`.
    *   **Resolution:** Image was pinned to `devlikeapro/waha:noweb-2026.7.2` in `docker-compose.yml`, which resolves this regressive bug and exposes the new `WAHA_NOWEB_WA_VERSION_FORCE` env var to override WhatsApp Web client version fingerprints in case of future blockages.
    *   **Alert Integration:** Added the `WAHA_SESSION_STUCK_STARTING` CRITICAL alert trigger to the monitoring daemon to catch any future startup stuck issues immediately.

## Operational Upgrade Protocols
1.  **Changelog Inspection:** Before executing any docker updates or pulling new images, check the official WAHA Changelog at `https://waha.devlike.pro/docs/overview/changelog/` to screen for breaking changes.
2.  **Staging-First Validation:** Never upgrade the WAHA image in the production environment directly. Verify all session statuses (`WORKING`, `SCAN_QR_CODE`) and message webhook processing in the staging environment first.
3.  **No Late-Tagging:** Do not use the `:latest` or `:noweb` tags without version numbers in production deployments. Always use the fully qualified version-pinned tags to prevent automatic updates from introducing breaking changes.

## AI Router Shadow Mode - Feature Rollout Protocol (2026-08-02)
Fitur observasi router (`AI_ROUTER_ENABLED=true` + `AI_ROUTER_SHADOW_MODE=true`) menulis evaluasi ke tabel
`ai_router_evaluations`. Rollout shadow mode WAJIB mengikuti urutan ini (runbook lengkap: `README.md`):
1.  **Prisma:** `npx prisma generate` + `npx prisma migrate deploy`. Jika error `relation "children" already exists`,
    fix sekali: `npx prisma migrate resolve --applied 20260802000000_add_children` lalu deploy ulang.
2.  **Verifikasi drift:** `npx prisma migrate diff --from-url "$DATABASE_URL" --to-schema-datamodel prisma/schema.prisma --script`
    harus output `-- This is an empty migration.`.
3.  **Smoke test:** 1 pesan asli -> cek row muncul di `ai_router_evaluations`; lalu jalankan
    `npx tsx src/scripts/check-router-accuracy.ts --days=7` sekali.
4.  **Nyalakan shadow mode di production** HANYA setelah 3 gate lolos (escalation >= 98% 7 hari berturut-turut,
    mismatch MEDICAL_CONCERN = 0 hard-zero sejak hari ke-1, UNMAPPED < 5%). Jadwal cek: hari ke-1, ke-3, ke-7.
5.  **Jangan pernah pakai `prisma generate --no-engine`** untuk workaround dll terkunci — hasilnya client
    Accelerate-only (`P6001`, URL harus `prisma://`). Matikan proses yang lock engine dulu, generate penuh.

## Live Chat Panel (SSE) — Deployment Notes (2026-08-03)
Endpoint real-time: `GET /api/admin/live-chat/events` (Server-Sent Events, satu kanal per tenant `livechat:{tenantId}` via Redis pub/sub).
1.  **Reverse proxy (nginx/Caddy):** WAJIB matikan buffering agar event sampai real-time — nginx:
    `proxy_buffering off;`. Backend sudah mengirim `X-Accel-Buffering: no` (dihormati nginx) +
    `Cache-Control: no-cache` + `Connection: keep-alive` + heartbeat `: ping` 15 detik (anti-idle-timeout balancer).
2.  **Redis WAJIB healthy:** pub/sub hub memakai `REDIS_URL`. Kalau Redis down, fallback in-memory EventEmitter
    (event hanya sinkron dalam satu instance — multi-instance TIDAK sinkron) + alert CRITICAL `queue.service`.
3.  **Balancer idle-timeout:** jangan putus koneksi idle — heartbeat 15s sudah mengirim data, tapi sesuaikan
    idle-timeout balancer bila lebih ketat.
4.  **Multi-instance:** SSE 1 kanal per tenant; balasan admin dari instance mana pun terpublish via Redis,
    klien SSE menerima event lintas instance.
5.  **Konek WAHA via QR (Fitur 1):** `GET /api/admin/whatsapp-provider/qr` + `POST /api/admin/whatsapp-provider/session/start`
    memakai session id per-tenant (`tenant.waha_session_id`, fallback env `WAHA_SESSION` saat DB down).
    Asumsi v1: satu instance WAHA (`WAHA_BASE_URL` global).
